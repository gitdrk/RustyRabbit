Signal path

From a click to the hardware

Every API call is a plain GET to /cgi-bin/<name>. inetd starts a fresh busybox httpd, which starts a fresh bash script, which then reaches the hardware in one of four ways. Physical input goes the other way: daemons announce button presses and RFID tags on D-Bus, and a long-running shell loop reacts to them.

D-Bus (LED, camera, button, RFID) Direct binary (ears) Media player (speaker) Network call

From time on the device: bash -c true 0.036 s, the three includes 0.240 s, the whole get_version script 0.305 s, status 1.019 s. A static file over HTTP answers in about 0.02 s.

Hardware or CGI? Both, in layers. The web server is fast. The first 0.3 s of every call is software: bash re-reading the same helper files on a 200 MHz chip. The next half second, on calls like status, is also software: dozens of tiny programs started one after another. The multi-second calls are the scripts choosing to wait for the hardware: a clip playing to the end, or the ears homing before they move.

0.3 s

Fixed CGI cost

Paid by every call. bash starts, then parses setup.inc, url.inc and utils.inc again. Nothing is kept between requests.

+0.4–0.8 s

Process spawning

Each killall, logger, ifconfig or echo | cut costs 10–30 ms on this CPU. status and sound_list run dozens.

+1–6 s

Waiting on purpose

sound holds the reply until madplay finishes. ears homes both motors first unless you pass noreset=1. The camera adds about 2.5 s.

timeout

Internet

Speech depends on VoiceRSS. With no route out, the call hangs until it times out.

Opportunities

What could be faster or better

Grouped by how much they touch the rabbit. The first group needs no change on the device at all.

Call it smarter

no device change

Always send noreset=1 to ears

6.1 s → 0.9 s

The reset is a full mechanical homing pass. Do it once at startup or after a reboot, then move ears directly.

Don't wait for sound replies

frees the caller

A sound?id= reply arrives only after the clip ends. Send it with a short client timeout and move on, or play through sound?url=, which backgrounds mplayer and returns after about a second.

Make speech on your PC, play it on the rabbit

works offline

Generate an MP3 with any modern voice on your own machine, serve it on your LAN, and call sound?url=http://your-pc/…mp3. This skips VoiceRSS entirely and sounds far better.

Use nomemory=1 for status lights

no file write per call

Without it, every LED change writes /usr/openkarotz/Run/led.color. For frequent automation colors, skip the write.

Health-check with get_version, not status

1.04 s → 0.33 s

Cache sound_list, voice_list and moods_list on your side; they only change when files are added.

Send one command at a time

fewer surprises

Scripts call killall led, killall madplay, and ears_reset kills everything. Overlapping requests cancel each other. Put a small queue in front of the rabbit.

Restore its internet route

fixes tts

Check the rabbit's gateway and DNS in your router. The clock also reads 1970, so it has no time sync either.

Small edits on the rabbit

only if you ever choose to

Storage is not the constraint you expected: /usr has 146.9 MB free. These are each a few lines in existing scripts, and the originals can be copied aside first.

Background madplay in PlaySound

5.67 s → 1.11 s (tested)

Add & to one line in utils.inc. Tested on a copy held in RAM: sound?id=bip1 returned in 1.11 s and the clip still played to the end. The rest of that second is the CGI startup plus the killall and logger calls. Speech has its own madplay call in the Python tts script and would need the same change there. Button and tag events play two clips back to back through the same function, so a real edit should background only the web call.

Slim down status

≈1.0 s → 0.4 s

Read MACs from /sys/class/net/*/address, count files with bash globs, and call df once.

Drop the per-call logger and repeated killall

−50 to −150 ms

Combine the kills into one command and log only errors.

Replace CGI with one long-running process

0.3 s → ~0.02 s

Python 2 is already installed. A single small HTTP server that stays running would skip the bash startup on every call, and it could push button and tag events out as webhooks.

Security

worth knowing

Anyone on your network is root on the rabbit

high

Telnet accepts user karotz with a blank password and gives a root shell. The web API has no login (A:*). Keep the rabbit on a guest or IoT network.

Web parameters reach eval

high

url.inc builds curl commands with printf and runs them with eval. Input filtering strips backticks and $( but not quotes, so URL parameters can likely run shell commands. I did not test this.

Triple click reboots

low

Hard-coded in dbus_watcher. Fine to know if a child is pressing the head.

Method: telnet as karotz, read-only commands only (cat, ls, ps, grep, time on read-only scripts), plus HTTP timing from 192.168.1.72. The LED, ear, sound and snapshot tests were returned to their starting state: LED off, ears reset. One test snapshot was added to Snapshots/.
